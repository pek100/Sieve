# Task: behavioural AdGuard detection and an ordinary pause

Stream `coexist`, branch `wf-coexist`. Spec: `docs/plans/2026-10-18-slice-3-attribution-and-cpu.md` section 4 "Ordinary AdGuard pause"; `docs/plans/2026-10-17-https-filtering.md` 1.7.

## Goal

The engine refuses to route when AdGuard for Windows **is intercepting**, not when its service is in some state. The app's Pause AdGuard button then works without any disable-and-kill step: after `sc stop`, AdGuard's service sits in StopPending for good, filtering is off, and Sieve routes.

Done means:

- StopPending and not intercepting: the engine routes.
- Running and intercepting: the engine refuses, as it does today.
- The app says what is true in each state, and never waits for a `Stopped` that will not come.

## What is wrong today (read from the code)

| Place | Today | Effect with real AdGuard |
|---|---|---|
| `coexist::adguard_running` | any state but stopped counts as running | a paused AdGuard blocks Sieve forever |
| `coexist::classify(tables, adguard_running)` | the blocker follows the service state | same |
| `src-tauri/src/adguard.rs` `change(Stop)` | waits 30 s for `ServiceFact::Stopped` | every successful pause reports "still Stopping after 30 s" |
| `src-tauri/src/adguard.rs` `change(Start)` | sc code 1056 counts as "nothing to do", then waits for `Running` | never reached from StopPending, so a 30 s failure if it were called |
| `adguardOffer` in `src/core/engine.ts` | offers `start` only on `stopped`, nothing on `stopping` | after a pause there is no offer and no explanation |
| `ADGUARD_PAUSE_TEXT` | "until you start it again here" | false: `sc start` cannot resume a StopPending service |
| `engine-mock.ts` | pause moves to the `filtering` example, whose AdGuard is `stopped` | tests prove a flow the real AdGuard never takes |

Facts about AdGuard (observed live 2026-10-18, from its own log and SCM events):

- `sc stop` stops filtering within about 1 s, then logs that it leaves the service running, so the process stays alive in StopPending.
- `sc start` on that service returns 1056.
- Resuming needs AdGuard's own protection toggle, a kill and start, or a reboot.
- `adgnetworkwfpdrv` and `adgnetworksockdrv` stay loaded while paused.

The service is `Stopped` on this PC now (read 2026-11-05), so no live row shape could be read while planning.

## Design decisions

1. **The question is answered by a test connection from the engine.**
   - The engine opens one TCP socket to a documentation address on port 443 (`192.0.2.1:443`, RFC 5737; `[2001:db8::1]:443`, RFC 3849, when IPv4 has no egress). No server exists there, so nothing real is contacted.
   - No payload is ever written. The socket closes at the end of the window.
   - Why this and not loopback: E4 says `FilterLocalhost` is a setting a user can turn off, and loopback is not the path that breaks. Probe run 2's failure was outbound sockets being captured. Port 443 and a public-range address are outside AdGuard's default exclusions (E4).
   - If live proof L1 shows AdGuard skips documentation ranges, the fallback is a loopback probe. That choice is made then, on evidence, not now.

2. **Two witnesses, either one is enough (S3).**
   - Connect completed within the window. Nothing can answer that address, so someone local did.
   - A row in the owner table owned by AdGuard's process that touches the probe: its remote end is the probe's local end (the proxy's accepted socket), or its remote end is the probe's destination (the proxy's upstream socket).
   - Otherwise AdGuard is not intercepting.
   - The row shape is a model, not an observation (L1). The connect witness is what keeps the verdict safe if the model is wrong.

3. **Safety asymmetry (S24).**
   - A connect that completed with no AdGuard row, while AdGuard's service is alive, counts as intercepting. The failure it prevents is the real one: two interceptors looping, curl timing out. The cost is a network that answers documentation addresses keeping Sieve waiting on a PC that has AdGuard.
   - A probe that cannot run (socket or table read error) is an `evaluate` error, which gives the existing `Blocker::Setup` path and routes nothing. Same path as a failed service read today.
   - No egress for either family is not an error: bring-up already refuses with "no default route".

4. **The service state only gates the probe.**
   - Absent or stopped means no interception and **no packet at all**.
   - Any other state means probe.
   - A PC without AdGuard therefore never sends a test packet, and the switch-off state keeps its no-timer idle (plan 6).

5. **AdGuard's process comes from the service manager, not an image name (S49).** `QueryServiceStatusEx(SC_STATUS_PROCESS_INFO)` gives the state and `dwProcessId` in one call, with the query access the engine already uses. `ADGUARD_SERVICE` stays the one name, and no `AdguardSvc.exe` string enters the engine.

6. **Drivers and adapters are not interception signals.**
   - The drivers stay loaded while paused, so they are not read at all.
   - An AdGuard VPN adapter is a tunnel adapter like any other, and `classify` already handles it as a VPN. It is a different product from AdGuard for Windows and never reads as interception.
   - AdGuard intercepting still wins over a VPN. A paused AdGuard with a full-tunnel VPN gives the `Vpn` blocker.

7. **The probe socket is pinned like every engine socket.**
   - With the TUN up, an unpinned SYN to `192.0.2.1` would enter Sieve's own stack and complete, a false "connected". It uses `route::pin::egress`.
   - The socket setup moves out of `stack/relay.rs` (`Relay::egress_socket`, `pin_to_interface`) into `route/pin.rs`, second use. Relay behaviour stays the same.
   - Redirection happens before routing, so pinning does not hide AdGuard.

8. **One window, no hysteresis.**
   - `PROBE_WINDOW = 250 ms` (declared, annotated).
   - `tokio::time::timeout` polls the inner future first, so a late timer on a loaded machine still sees a finished connect. No "N clear verdicts" ladder (S50).
   - A wrong clear verdict lasts at most `RECHECK_EVERY` (5 s).

9. **`evaluate` becomes async** so the 250 ms wait does not hold a runtime worker.

10. **No wire change.**
    - `Blocker::Adguard { service }` now means "is intercepting". The kind and fields stay, so IPC stays v2 and the probe stays v2 (S51: the app reads the verdict from the blocker it already gets).
    - Only the doc comment in `sieve-ipc/src/lib.rs` changes.
    - The stream brief names `engine-ipc-v1.json`; the repo has `engine-ipc-v2.json`, and neither is touched.

11. **App flow.** `adguardOffer` becomes `"pause" | "start" | "paused" | null`, from facts:

    | Service (`probe.adguard`) | Engine | Offer |
    |---|---|---|
    | `running` | phase `adguard` | `pause` (button) |
    | `stopped` | any | `start` (button; `sc start` works from here) |
    | `stopping` | routing switch in force, phase not `adguard` | `paused` (text, no button) |
    | `stopping` | phase `adguard` | null; the detail line says Sieve is re-checking |
    | anything else | any | null |

    `paused` needs the switch in force because with the switch off the engine gives no verdict, and "no longer filters" would be an unverified claim (S11). No new phase.

12. **`change(action)`** gets a pure `reached(action, fact)`: Stop ends at `Stopped` or `Stopping`, Start ends at `Running`. The elevated commands and law 8 stay exactly as they are. No kill anywhere in product code.

13. **The test runners stay as they are.** `scripts/live/run-slice-3-auto.ps1` and its disable-and-kill path are the plan's named test workaround, and they keep working: they stop and start AdGuard by their own means. Only the manual `engine-route.ps1` wait changes (step 9).

## Shape of the code (coexist.rs)

```rust
pub enum AdguardService { NotRunning, Alive { pid: Option<u32> } }   // absent and stopped are one consequence
pub struct ProbeObservation { pub local: SocketAddr, pub dest: SocketAddr, pub connected: bool, pub rows: Vec<OwnerRow> }

pub fn intercepted(obs: &ProbeObservation, adguard_pid: Option<u32>) -> bool;      // pure, the witnesses
pub async fn adguard_intercepts<F, Fut>(service: AdguardService, probe: F) -> Result<bool, String>; // gate; `probe` is the seam
pub fn classify(tables: &NetTables, adguard_intercepting: bool) -> Coexistence;    // body unchanged

// Windows only:
pub fn adguard_service() -> Result<AdguardService, String>;
pub fn probe_dest(tables: &NetTables) -> Option<(SocketAddr, Egress)>;             // pure: v4 first, then v6
async fn observe<S: OwnerSource>(socket: socket2::Socket, dest: SocketAddr, window: Duration, source: &mut S) -> Result<ProbeObservation, String>;
```

`observe` takes a built socket and an `OwnerSource` (the existing trait), so a test can drive it on loopback without pinning. It reads one table, the probe's family, once, after the connect finished or the window ended.

## Open questions (Michael's)

1. **There is no one-click undo after a pause.** "Start AdGuard again" cannot work from StopPending: `sc start` returns 1056, and a kill is ruled out of product code.
   - Built here: the app says to use AdGuard's own window or restart, and shows no button. Start stays for a truly stopped service.
   - Alternatives, only if he wants them: an "Open AdGuard" button (launching its UI, not a filter action), or asking for a kill-and-start through the prompt, which would change law 8 and his own rule.
   - Does not block the build.
2. **A test packet.** While the switch is on and AdGuard's service exists and is not stopped, the engine sends one SYN every 5 s to a documentation address.
   - It carries no data and reaches no server, but it does leave the PC (when AdGuard is not intercepting), and firewall logs would show it. While not routing, the app's connection list can briefly show the engine's row.
   - A PC without AdGuard, or with it fully stopped, sends none.
   - Built on the assumption this is acceptable. If not, the cadence is the one thing to change (for example, probe at bring-up only), which would leave a resumed AdGuard undetected until the next route change.
