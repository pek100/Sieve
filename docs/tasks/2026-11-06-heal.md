## Goal

A client that rejects Sieve's certificate costs at most one failed request per (app, host) on strong evidence, and is never excluded for connections it later uses. The next connection of that pair passes through untouched. The user is told once per app, sees why each site is not decrypted, can add and remove their own sites, and can try again.

`filtering.https` stays unavailable: this stream builds behind it and does not unlock it. Do not change `ENGINE_SLICE_6`, `unavailableUntil`, law 11, `SCOPE` or `flow::relay::relay_tcp`.

## Design decisions

**D1. One quantity, its law written directly (S18, S50).** `heal/score.rs`, pure, `now_ms` passed in (S15), `f64`:

```
decayed(v, dt) = v * 0.5^(dt / HALF_LIFE)      // credit decays toward 0 by the same law
silent close:  v = decayed + 1;  excluded when v >= EXCLUDE_AT
used conn:     v = max(decayed - 1, -MAX_CREDIT)
fatal alert:   excluded at once
try again:     v = 1 at now
```

Declared in `heal/dials.rs`, each annotated (S25):
- `SILENT_CLOSE_MS = 2000`, `HALF_LIFE_MS = 30 * 60_000`;
- `EXCLUDE_AT = 1.5`: exactly "the second close arrives within one half-life of the first" (`0.5^(gap/h) + 1 >= 1.5` is `gap <= h`);
- `MAX_CREDIT = 2.0`: a pair that carried requests needs 4 quick closes instead of 2. Bounded, so a client that starts pinning after an update still heals, and fatal alerts ignore it. Deviation from the plan's wording; see Q2.
- `FATAL_ALERTS`: the plan's six alerts, one table;
- `NOTICE_WINDOW_MS = 10 * 60_000`, `MAX_PAIRS = 4096`, `NOTICE_HOSTS_MAX = 20`, `NOTICE_RING = 64`.

TENSION recorded in `dials.rs`: `SILENT_CLOSE_MS` is a hard edge on a weight, a deliberate policy choice from the plan (S18's discrete clause, S50). A close after it says nothing, not "a little". Scores live in `crate::lru::Lru`, keyed by (exe file name lower case, host lower case), memory only: losing one costs one more close. Why no second ladder: retry's seed and credit are the same equation and the same threshold.

**D2. Credit once per connection.** `handle` becomes `if !ctx.seen.swap(true, ..) { ctx.watch.request_seen(..) }`. The trait's doc says "the first request of a connection". `Watched` in `tls/tests.rs` keeps working; its count now means connections.

**D3. Strong evidence wherever it arrives.** `Ended` gains `client_alert: Option<AlertDescription>`, read with `rustls_error` from the server future's error (h1 and h2), and `client_ended` is false for `is_parse()` as well as the timeout. In `intercept`: `client_ended && !seen` with an alert calls `handshake_failed(pair, alert)`, else `closed_without_request`. How the watch weighs what it hears:

| Heard | Weight | Why |
|---|---|---|
| Alert in `FATAL_ALERTS` | excluded | Plan 4.3 |
| Any other alert, or `handshake_failed(None)` (a close, a refusal rustls names itself, `CLIENT_HANDSHAKE_TIMEOUT`) | +1, no window | The client did not accept our flight. Passing through is the fail-open answer whichever side is at fault. No new seam for the timeout, which is one more failed attempt |
| `closed_without_request` within `SILENT_CLOSE_MS` | +1 | Plan 4.3 |
| `closed_without_request` later | nothing | An idle preconnect |
| `request_seen` | -1 | Plan 4.3 |
| A close by the engine, an upstream, a plain copy | never reaches the watch | Slice 6, already pinned |

**Superseded 2026-11-08 (live bug: Edge and Chrome 157 excluded www.google.com, static.cdninstagram.com, cdn.discordapp.com).** The two `closed_without_request` rows and "any other alert" after the handshake are replaced; the rule is in plan 4.3's note of that date. The seam is now `handshake_failed`, `accepted`, `request_seen` and `ended(Option<Silence>)`, so the watch knows which connections of a pair are open. Tests renamed with it: `two_silent_closes_within_the_half_life_exclude` became `a_client_closing_during_the_handshake_again_and_again_is_excluded`, and `two_silent_clients_exclude_and_the_third_passes_through` became `repeated_silent_clients_exclude_and_the_next_passes_through`.

**D4. History lives on the entry, in the file that exists (S29, S52).** `AutoEntry` gains two defaulted fields, `#[serde(default)] retries: u32` and `#[serde(default)] retrying: bool`, version unchanged (S39: a v1 file loads, and `OnDisk`'s `deny_unknown_fields` does not reach `AutoEntry`, so a rolled-back engine reads a new file too). A `retrying` entry is left out of the snapshot and the rows. So:
- `ExclusionSlot::remove_auto` is renamed `try_again(pattern, app, now_ms) -> bool` (it takes the clock, F8) and sets `retrying`, `retries += 1`. False when absent or already retrying. Its two test call sites follow. `try_again_app(app, reason, now_ms) -> usize` is the bulk form (D7).
- `add_auto` returns true when the entry newly excludes. Over a `retrying` entry it keeps `created_ms` and `retries`, clears the flag: "the entry comes back with its history". Over a held entry it moves it to the newest place and keeps its first date too: a second refusal in flight must not lose the date (`retry_refuse_refuse_keeps_the_first_date`; `adding_a_held_entry_again_makes_it_the_newest` still pins the place).
- `AutoEntry::for_app(host, exe, reason, now_ms)`: `Pattern::Exact`, app is the exe's file name lower case, what `Exclusion::app_matches` compares. A flow with no exe never gets here (`unknown_exe_never_intercepts`).
- `cap` counts retrying entries, so the file stays bounded; an evicted one just loses its history.
- `Heal::try_again` also seeds the score to 1, so a client that still pins with silent closes is excluded by one more, not two. After a restart the seed is gone and it takes two, which is harmless. A rejected try is one failed request, matching the plan's "works after at most one".

Rejected: a second `heal.json` beside `exclusions.json` (two files for one fact, and a generic `Writer` to carry it).

**D5. Notices: engine groups, app renders.** `heal/notices.rs`, pure, clock passed in. A new pinning exclusion (`add_auto` true) joins the open group of (session, exe file name) if under `NOTICE_WINDOW_MS` from the group's first exclusion, a fixed window so a slow trickle cannot hold one group open forever; else it opens a new group. `HealNotice { id, session, exe, hosts (first NOTICE_HOSTS_MAX), total, rev }`, in a ring of `NOTICE_RING`, memory only, session scoped at the pipe with the existing rule (`visible_to`'s: a client gets its own session's). `Pair` gains `session` (F9). `auto:client-cert` and `auto:ev` raise no notice: the plan's text is about rejecting, and they appear as rows.

Pull, not the Subscribe stream: the stream is up only while routes are, and adds a Rust ring; the engine controller already reads the certificate once per `ENGINE_POLL_MS`. App side (`src/hooks/use-heal-notices.ts`, mounted once in `AppShell`): for a new group id, push one toast with the action "Show" (next/navigation, `exclusionsHref(app)`). For a new `rev` of a group whose toast is still in `notices.list()`: dismiss and push the new text. Otherwise nothing: the row is there and the user was told about this app in this window (F12), so "one notice per app" holds. No change to the bus. As built, three points this paragraph left open: a group counts distinct hosts; "Try decrypting again" closes the app's groups, so a refusal of what was tried opens a new group and a new toast, with the count starting over; and the engine outlives the window, so a controller's first read is a baseline that is not toasted, and an exclusion made while no window was open shows as a row only. - "<App> rejected Sieve's certificate for <host>. Sieve stopped decrypting it."
- "<App> rejected Sieve's certificate for 3 sites. Sieve stopped decrypting them."

`<App>` is the running app's name for that exe from the snapshot, else the file name.

**D6. IPC: three new message types, no bump (lib.rs header: a new type is no shape change).** Appended to `CLIENT_TYPES` and `ENGINE_TYPES`, with fixture examples:

A row names its `line`, `app` and `reason`, so it takes back that row and not another reason's entry on the same host. `line` and `reason` None with an app is the bulk form for that app's `auto:pinning`. Both reads run only while `httpsInForce(e)`. A failed read keeps the last rows and sets `exclusionsError`, like the log controller. 7.3's "no sign, export or mint" stays true by inspection and by test.

## Open questions for the user

**Q1. How does the live check reach a non-browser client?** Browsers first means curl, Discord and Steam are never intercepted, so slice 7's own live acceptance cannot run, while the decision table waits on that acceptance before widening. Default: the `live-scope` cargo feature (D10), a diagnostic build like `relay-experiments`, never in a release. Alternative: prove healing only with a browser that rejects the root, which proves the path but not "Discord works". Widening scope for users stays your call after U1 to U5, and is not in this stream.

**Q2. Credit for a pair that has been used.** The plan's literal reading excludes after two quick failures with no success between them, whatever came before. Default: a used pair earns up to `MAX_CREDIT` 2, so it takes four quick closes. Cost: a client that starts pinning silently after having worked fails up to two more times, and fatal alerts are unaffected. Without it, two redundant sockets on a busy site can turn off URL filtering there for that browser. U5 measures it, and the dial is one number.

**Q3. Mass rejection by a client that merely lacks the root (F7).** Default: per-host entries as designed, with the notice's grouping and one "Try decrypting all again". Alternative: when one exe rejects many hosts in a short time, treat it as "this client does not trust the root", which needs an app-level entry and a new dial. Not built until U6 shows it is worth a second mechanism (S52).

**Q4. Rows across Windows sessions.** The store is machine-wide, so a second account already admitted by the pipe's DACL would see another session's hosts in the list, though not in notices. Default: accept, since the DACL admits only the enabling user, SYSTEM and Administrators. Alternative: record the session on auto entries and filter rows, at the cost of a session id that means nothing after a reboot.
