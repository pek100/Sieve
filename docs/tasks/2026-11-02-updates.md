# Slice 13: signed updates (task plan, stream `updates`)

Status: planned, nothing built. Branch `wf-updates`, worktree `.claude/worktrees/wf-updates`, cut from main at f0fe2cb.
Spec: `docs/plans/2026-10-17-https-filtering.md` 7.5, slice 13, 1.5 (Updates), 5.5, 7.1, 7.3, and the two decision rows at its top (Scriptlet resources, Signed updates).

## 1. Goal

The engine service is the only updater. It fetches app and engine releases, the scriptlet resource bundle and Sieve-owned lists, verifies each one's minisign signature against a public key compiled into it, checks the signed kind and a signed version that must rise, and only then replaces files: in the locked install folder for releases, in admin-only ProgramData for data. A new engine that does not come up is rolled back. The unelevated app can only send `RequestUpdate {}` and show the result.

Done means: every acceptance item in section 5 passes offline, and everything that needs the real machine is in section 6, unclaimed.

Out of scope: generating the real key pair, the real update host, retiring the resource pin if slice 9 has not landed (section 7, step 11), third-party filter lists (they keep their own channel, plan 5.4).

## 2. Facts read from the code and a probe

Each of these shaped a decision below.

- A throwaway crate (2026-11-05, in a scratch folder, nothing committed) confirmed: `minisign-verify` 0.2.5 verifies with `allow_legacy = false` what `minisign` 0.8.0 signs, exposes `Signature::trusted_comment()`, refuses a changed byte and another key. `PublicKey::from_base64` takes the key line, `PublicKey::decode` the whole two-line text.
- The same probe: a secret key's first line is free text (the probe got `untrusted comment: test`), so a header grep alone misses one. The second line is the reliable witness: it starts `RWQAAEIy` unencrypted and `RWRTY0Iy` encrypted.
- Not probed, from memory of Tauri's format, so the law covers it either way: `tauri signer generate` wraps the whole key file in base64, so its header would appear base64 encoded.
- Not probed yet, and the first thing step 4 pins with a real-file test: on Windows `std::fs::rename` replaces the destination atomically on one volume (MoveFileExW with replace), fails on a mapped running image, and can rename that image away. D12 and D17 rest on this; if the test disagrees, stop and revisit them.
- `src-tauri/target/release/nsis/x64/installer.nsi` (read 2026-11-05): `/UPDATE` is parsed in `.onInit` and sets `$UpdateMode`. `utils.nsh` `CheckIfAppIsRunning`: under `/S` it force-closes a running `sieve.exe` through Restart Manager. `/R` relaunches the app afterwards, which must not be passed from session 0.
- `hooks.nsh` pre-install runs `restore` through the registered ImagePath and re-locks the folder; post-install runs `install`, which starts the service.
- `service::image::install_chain` checks every top-level entry of the install folder and refuses on any non-admin write right. A staging folder and `.old` files inherit the lock, so they pass. It does not descend into subfolders.
- `runner::service_main` runs the folder check before reporting Running. `ipc::server` answers a non-`sieve.exe` client with one `NOT_ALLOWED` frame (test `the_owner_gets_through_the_dacl_and_a_foreign_exe_is_refused`). `pipe_sddl` admits SYSTEM.
- `scm::start`, `scm::stop` and `wait_for` exist (private); `policy::write_atomic` is the atomic write (private); `stack::relay` holds the pinned-socket code around its `setsockopt` (private).
- The engine has no TLS client and no HTTP client on main. `Cargo.lock` has no rustls or hyper. cmake is on PATH, nasm is not.
- `docs/conventions.md` section 8: tests needing a server use `tokio::io::duplex`, not 127.0.0.1 (AdGuard filters localhost on this machine).
- The law and task text call the IPC fixture `engine-ipc-v1.json`; the real file is `src/data/fixtures/engine-ipc-v2.json`, at PROTOCOL 2. `tests/laws/engine-ipc.test.ts`'s header comment still says v1.
- `tauri.conf.json`, `package.json` and the engine workspace all say version 0.1.0.

## 3. Design decisions

Design gate answers (clean-architecture): no existing law covers signed artefacts, so `update/` is a new mechanism the plan admits explicitly. Each quantity has one owner, named below. Retired by it: the resource pin (once slice 9 consumes the signed bundle).

| # | Decision | Reason |
|---|---|---|
| D1 | Verify with `minisign-verify` (no dependencies). Tests sign with `minisign` as a dev-dependency only, generating the pair in memory inside the test. Prehashed signatures only (`allow_legacy = false`). | The verifier is small and is what Tauri's updater uses. Signing with the real tool in tests is a cross-witness of the format (S3). A hand-rolled signer would test only itself. |
| D2 | `update/trust.rs`: `pub const PUBLIC_KEY: &str = "PLACEHOLDER: ..."`, clearly marked. `TrustAnchor::parse` turns a placeholder into `Refusal::NoKey`. Every verify takes a `&TrustAnchor`, so tests pass their own; only `win.rs` and the runner call the production constant. | Fail closed: a build with the placeholder verifies nothing and fetches nothing. Never a random stand-in key, which someone could hold the secret half of. |
| D3 | Update host: `UPDATE_BASE_URL` constant, placeholder `https://updates.sieve.invalid/`. While key or URL is a placeholder the state is `not_configured` and the fetcher is never called. No redirects are followed. | `.invalid` cannot resolve, so no accident reaches the network. The host is the user's call (Q1). |
| D4 | Trusted comment grammar, parsed strictly: exactly `sieve-update kind=<k> version=<n>`, with `<k>` one of `app`, `engine`, `resources`, `index`, `list:<id>` (`[a-z0-9-]+`), `<n>` a u64 in plain digits. Anything else is `Refusal::BadComment`. | Plan 7.5. `index` is added beyond the plan's list: the plan says the index is "signed the same way", and without its own kind a signed list could be served as the index. |
| D5 | Index: `index.json` plus `index.json.minisig`, signed with `kind=index version=<n>`. Body `{schema: 1, version, expires_unix, artefacts: {"<kind>": {version, file, size}}}`, `deny_unknown_fields`. Read at most 1 MiB. `file` is a bare name (no separators, no `..`), fetched from the same host. `version` must equal the comment's and be at or above the last accepted index version. Expired: `Refusal::IndexExpired`, reported as `stale`, nothing applied. | Expiry stops a freeze; the rising index version stops serving an old unexpired index. Unix seconds need no date library. A signed `size` caps each download before any verification, so a hostile host cannot fill the disk. |
| D6 | No hash in the index. | Each artefact has its own signature; a hash would be a second owner of the same fact (S51). This replaces "verified against a published hash" in the first Scriptlet resources row, as the later Signed updates row and plan 5.5 already say. |
| D7 | The artefact's comment version must equal the index's entry for it. | Mix and match between two validly signed files is refused. |
| D8 | Version numbers: app and engine use `major*1_000_000 + minor*1_000 + patch`, computed at compile time from `CARGO_PKG_VERSION_*` (`release_number`). Data kinds use any rising integer. | One source of truth, the Cargo version, and a real baseline: with no record, a fresh install still refuses an older signed release. |
| D9 | Installed version: for `app` and `engine`, `max(record[app], record[engine], own release_number)`, because the installer carries both, so a lower `app` release would downgrade the engine. For data kinds, `record[kind]` or 0. | Rollback protection for the case a per-kind record would miss. |
| D10 | One state file `update-state.json` in `ProgramData\Sieve\engine`: `{versions, index_version, rolled_back: {kind: n}}`, plus `update-pending.json` while a release is in flight. Both use `policy::write_atomic`, made `pub(crate)`. A rolled-back version is not offered again; a higher one is. | Admin-only, as the plan requires. Without `rolled_back`, every check would offer the broken version again. |
| D11 | Data kinds: fetch, verify, then one `rename` of the staged file over `updates\<kind file>`, then raise the record. No `.old`. Staging: `ProgramData\Sieve\engine\updates\staging`. | One atomic rename is the whole swap. A crash between the rename and the record refetches and replaces idempotently. |
| D12 | **Deviation from 7.5's wording, same guarantee or stronger:** releases copy the current files to `*.old`, then rename the verified file over the real name, with the service stopped. 7.5 says rename the old aside, then rename the new in. | Rename-aside leaves a moment with no `sieve-engine.exe` at the ImagePath, and a power loss there needs a reinstall. Copy then atomic replace keeps a complete exe in place at every instant. `.old` still exists until healthy, as the acceptance list demands. A running image cannot be replaced, which is why the service stops first. |
| D13 | The release set: `engine` swaps `sieve-engine.exe` only (a wintun change ships in an `app` release). `app` sets aside every regular file in the install folder except the marker, derived from the listing, and runs the installer. | Derived, not enumerated (S49). |
| D14 | A small supervisor carries the swap: the verb `update-finish`, no arguments, running from a copy of the current exe at `<install>\update-staging\update-finish.exe`. It stops the service, sets aside, swaps (or runs the installer), starts the service, waits for health, then deletes `.old` or rolls back. All inputs come from `update-pending.json`. | A process cannot replace its own image, and rollback needs a process that survives the new engine failing at start. It runs from staging so the installer can overwrite `sieve-engine.exe`. A clean SCM stop records `stop_clean`, so an update never counts toward the crash loop. An unelevated caller cannot read ProgramData, so the verb does nothing for them. |
| D15 | **Interpretation of "reports healthy over the pipe":** after start, a new engine with a pending record connects to its own pipe and reads one frame. The frame is `NOT_ALLOWED`, as the exe is not `sieve.exe`, which proves the serve loop answers. If its own release number equals `to_version`, it raises the record and deletes the pending file. The supervisor polls for that deletion, up to `HEALTH_DEADLINE` (90 s). | The client check rightly refuses anything but `sieve.exe`, so the supervisor cannot hold a Hello. This uses the pipe literally and leaves `client_allowed` and `serve` unchanged. The number check catches a mislabelled release. |
| D16 | Service start recovery, one pure function `recover(pending, own_number)`: own equals `to_version` means continue to the health probe; own equals `from_version` means the swap never happened, so clear pending and `.old`; anything else means clear pending and report. Runs before anything else in `serve`. **Added by validation:** the installer copies `sieve.exe` first and the engine last, so own equal to `from_version` does not prove the swap never happened. The supervisor marks `swap_started` in the pending record once every `.old` is whole, before the first real file changes. If that mark is set and the real files differ from the `.old` set, or an `app` release added a file, the release is marked `rolling_back` and the old build restores it in place. | Handles a reboot in the middle, when no supervisor exists any more. |
| D17 | Rollback is one primitive for both kinds: rename `.old` over the real name; a file that refuses that (a running image) first renames to `.failed`, and comes back if `.old` still will not move. Stop the service first, record `rolled_back`, delete pending, start the service. | A running `sieve.exe` can be renamed, so this cannot jam on it. A stopped exe is replaced atomically, for the reason D12 gives: renaming it aside first left a moment with nothing at the ImagePath (amended 2026-11-06). Filtering fails open throughout: routes go with the stopped service. **Added by validation:** a file held open without delete sharing can outlast the retries. The verdict is written to the pending record (`rolling_back`) before any file moves, `rolled_back` is recorded and `.old` deleted only once the set is whole, and the marked release stays in flight: the supervisor keeps trying while no engine runs, the old build finishes in place, and any other build starts a new supervisor. |
| D18 | `RequestUpdate` carries no fields and has two effects, derived from state: while the state is `available {version}` it applies that version; otherwise it runs a check. The daily check applies data kinds and only reports a release. Checks are limited to one per `REQUEST_COOLDOWN` (5 min); over that the answer is `Error`. Every other answer is `Status`. | One message, as 7.5 says. The app cannot name a version, URL or path. "Check again" can never install something the user was not shown. |
| D19 | `EngineStatus` gains `update: UpdateStatus`, a tagged enum in the shape of `Blocker`: `not_configured`, `idle`, `checking`, `current`, `available {version}`, `applying {version}`, `stale`, `failed {message}`, `refused {message}`, `rolled_back {version}`. `version` is a display string derived from the release number. | The plan requires the reason to be shown in the app. One enum, each state with only its own fields. |
| D20 | Refusal reasons go to an injected log sink. In production that is `update.log` in the engine folder, capped at `LOG_MAX_BYTES` (64 KiB; at the cap it keeps the newer half). Tests use a memory sink. | The acceptance list wants listings identical after a refusal, and the plan wants the reason logged. A sink seam satisfies both; the listing test covers everything else. The cap is required because a hostile host can provoke a refusal every check. |
| D21 | The fetcher is a trait: `get(file, max_bytes, dest)` streams to a file and refuses past the cap. The real one (`update/https.rs`, Windows) is rustls with aws-lc-rs and `webpki-roots` (plan 2.7) over a pinned socket, HTTP/1.1, `Connection: close`, one status check, `Content-Length` or close-delimited, no chunked, no redirects. Pinned socket code is extracted from `stack/relay.rs` to `route/pin.rs` for reuse. | Its own sockets must bypass the TUN, or the loop guard refuses them. If `wf-encrypted-dns` lands a shared TLS client config first, use it (one owner). hyper does not earn a place for one GET. |
| D22 | Installer call: `<staged> /S /UPDATE /D=<install folder>` (`raw_arg`, `/D=` last and unquoted, as NSIS requires), with `TEMP` and `TMP` set to the staging folder. Never `/R`. Tauri's updater plugin is never added (law). | `/D=` keeps "the same folder" true even when the registry disagrees. NSIS unpacks plugin DLLs under TEMP, and SYSTEM's default temp is a folder users can write into; plan 7.5 says nothing user-writable is read back. |
| D23 | App notice, flat: a block of plain text and one button inside the Engine block (no chip, no container), plus one Home banner through the notice bus for `available` and for `rolled_back`, in the existing `CRASH_LOOP_BANNER` pattern. `not_configured`, `idle`, `checking`, `current` show nothing beyond one muted line for `current`. | Conventions 4 and 5. The app does not poll separately: `update` rides the existing 2 s probe. |
| D24 | `FIRST_CHECK_DELAY` 10 min after service start, then every 24 h, with `FAILED_RETRY` 1 h after a network failure. No persistence of the last check. | Boot stays quiet and a restart costs at most one extra fetch. S52: no extra state to reason about. |
| D25 | Shared files stay append-only. `PROTOCOL` becomes 3 and `SUPPORTED` `[3, 3]` unless main has already moved in this merge wave, in which case the stream takes that number with no second bump. The fixture is edited in place and **not renamed**; the orchestrator renames it once after the wave. `ENGINE_PROBE_VERSION` is treated the same way. | Parallel streams would otherwise conflict on the rename, and each would burn a protocol number no released client ever spoke. |

## 6. UNVERIFIED (live proofs, the user's; `docs/live/updates.md` gives each step)

An agent never runs any of these. None may be reported as passing until the user has run them.

1. The user's key pair: `minisign -G` on their own machine, the public key compiled in, the private key offline. The runbook must say to sign with `minisign -Sm <file> -t "sieve-update kind=... version=..."`, because `tauri signer sign` (from memory, the runbook's author checks it) writes its own trusted comment, and that `minisign` is not installed on this machine.
2. The real host: the real TLS fetch over the pinned socket, with routes up and with them down, and DNS resolution of the host while the engine routes.
3. The real swap in `E:\Sieve`: the staged file's inherited ACL passing the folder check at the next start.
4. The supervisor as a detached child that survives the service stopping; `stop` and `start` under the four trimmed privileges (`REQUIRED_PRIVILEGES`). Whether `update-finish` inherits a token sufficient for this is unknown.
5. The real installer as SYSTEM with `/S /UPDATE /D=`: the hooks, icacls `/setowner` under the trimmed token, `sieve.exe` force-closed, shortcuts and the uninstall entry written from session 0, `TEMP` in staging working for NSIS plugins, and `state.json` still holding the installing user's SID afterwards, with the unelevated app able to connect (the hook's `install` verb runs as SYSTEM).
6. A real new engine failing at start, rolled back by the real supervisor.
7. `sc qc` and the version in the app showing the new one; a re-served older release refused. This is plan 7.5's live acceptance.
8. Power loss during a swap (D12, D16). After a boot with a broken new engine and no supervisor, nothing rolls back: SCM restarts twice and stops, the network stays normal, and the user reinstalls. Known limit, stated to the user, not hidden.
   The same limit holds for a rollback still locked after the supervisor's hour, with a new engine that cannot start; its `.old` files stay.
   A power loss between the installer's copy of the new engine and its copy of Wintun is kept as healthy with the old Wintun beside it, since nothing tells it from a finished install. A power loss during an `app` install with the old engine still in place rolls back (D16), which a real reboot has not proved.
9. A healthy report followed by a crash seconds later is not rolled back; the existing crash loop stop handles it, fail open.
10. `tls_refuses_an_untrusted_root` proves rustls's refusal in memory, not the real chain to a real host.

## 8. Open questions for the user

The implementation proceeds on the stated default for each; none blocks offline work.

- **Q1. Update host.** Where will releases be served? This decides the URL constant and redirects. GitHub Releases redirects to another host, which D3 refuses as built; signatures make following redirects safe, but the plan says "the catalogue host". Default: the `.invalid` placeholder, no redirects, updates stay `not_configured` until you pick. If you pick GitHub Releases, allow redirects over validated HTTPS.
- **Q2. When do releases install?** Default per D18: never by themselves, only after you click Install update. A release stops the engine for some seconds and closes the app. Data kinds apply daily with no prompt. Tell me if you want releases automatic too.
- **Q3. Engine-only releases.** 7.5 lists both an `engine` kind and "one NSIS installer per release". An engine-only update whose protocol moved leaves the old app shut out ("Reinstall Sieve so both match"). Default: both are built as the plan says, and the runbook says to publish `app` for normal releases and `engine` only for a fix that does not change the protocol. Dropping `engine` would remove D13's first half if you never want it.
- **Q4. Checking while filtering is off.** The daily check contacts your host even when the user has filtering off, and the service description says that while off it "changes nothing on this computer's network". A fetch changes no network state, but it is a request nobody turned on. Default: check daily regardless, per the 2026-10-17 decision, because a stale engine is the worse outcome. The alternative is to check only while `filtering.engine` is on, or when asked.
