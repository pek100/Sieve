# Sieve conventions

How this repo does things, as built by the foundation (2026-10-17). The plan (`docs/plans/2026-10-17-parity.md`) says what to build; this file says how. The look comes from `docs/research/2026-10-17-parity/design-language.md`. If code and this file disagree, fix one of them in the same commit.

## 0. Sieve off means a normal network (the top rule)

Sieve off means a normal network. Sieve never writes persistent system network state (DNS servers, persistent routes, proxy settings, firewall rules that outlive the process). Everything Sieve changes disappears by itself when Sieve stops, crashes, is uninstalled or the PC reboots.

Why (2026-10-18): "Point Windows at Sieve" set every adapter's DNS to 127.0.0.1 and ::1. After a reboot Sieve was not running (launch at startup is off), nothing answered DNS, and the PC could not connect until the user reset DNS by hand. A startup recovery only works when Sieve itself starts. The user: "remove the Point Windows at Sieve feature; the engine will replace it with something that can't break the network." It was removed the same day (settings schema 3 drops `filtering.systemDns`).

What this means in code:
- No command, script or API call that sets DNS servers, adds persistent routes, sets a system or WinHTTP proxy, or adds firewall rules, and no elevation from the app. Law 8 (`tests/laws/normal-network.test.ts`) greps `src` and `src-tauri/src` for those names. One elevation is allowed, by the user's decision of 2026-10-17 (offer to pause AdGuard; AdGuard has no supported pause from outside): `src-tauri/src/adguard.rs` runs `sc.exe stop|start "Adguard Service"` from System32, with fixed arguments, through the Windows prompt, only when the user clicks; law 8 holds it to exactly that.
- The engine (slice 3) adds routes only on its own Wintun adapter, in the active store, through `route/apply.rs` with a `SieveLuid`, and never touches DNS settings. Law 12 (`tests/laws/engine-network.test.ts`) pins both by name.
- Reading is always allowed. The one Windows DNS fact Sieve uses is read only (`windns`, the safety net in section 3).
- Anything that changes traffic lives only as long as the process that made it: a socket, a listener, an adapter or route that goes when its owner's handle closes.

Acceptance checks every traffic-changing slice must pass (the engine's slices in `docs/plans/2026-10-17-https-filtering.md` list them), run by the user with a verifier reading the evidence:
- **Kill test.** With the feature on and working, `taskkill /F` the process that owns it. Within 5 s, name lookups (`Resolve-DnsName example.com`) and HTTPS (`curl -I https://example.com`) work, and `route print`, `Get-DnsClientServerAddress`, `netsh winhttp show proxy` and the firewall rule list match the before-listing.
- **Reboot test.** With the feature on, reboot with Sieve (and its engine) not set to start. After sign-in, lookups and HTTPS work and the same listings match the before-listing.
- **Uninstall test.** With the feature on, uninstall Sieve. Lookups and HTTPS work, the listings match, and nothing of Sieve's is left in the network settings.

Import direction: `app -> components -> hooks -> data -> core`.
- `src/core` imports only from `src/core`, plus `import type` from `@/data/protocol`. No React, Next, Tauri, DOM, `Date.now`, `new Date()`, `Math.random` (law 5). Time inside a derivation is the newest snapshot's `t`.
- `src/data` may import `src/core` (for example `isActiveFlow`).
- Components read data only through hooks (`useSieve`, `useSetting`, ...), never by importing a source or the store directly.

## 6. Settings and data switches

- Engine-dependent data switches declare `needsEngine: true` in the registry. Settings uses the existing `Lock` with the phase's reason; components never name a setting key to lock it. `engineTakesPolicy` requires a successful read, a running service and an accepted handshake with Status. Checking, unreadable, not installed, not running, refused and incompatible therefore lock the row and prevent the controller sending `setPolicy`. A stored wish is preserved until the engine can accept it; a locked row shows `policy.engine` when known, otherwise off. Refused copies direct the user to open Sieve from the Start menu. The registry law ties the marked switches to the policy payload; `engine-lock.test.tsx` walks the registry and mock phases, and the controller tests cover refused writes and later recovery.
- The top-bar wordmark includes flat, muted "Dev build" text only when `process.env.NODE_ENV !== "production"`. Use that direct build-time expression, never a runtime Tauri check or dynamic environment lookup. The bundled Next guides `01-app/02-guides/environment-variables.md` and `static-exports.md` document command defaults and build-time export; `next/dist/build/define-env.js` replaces the environment expression for the client too. `wordmark.test.tsx` stubs development and production renders. The build finishes with `scripts/check-release-label.mjs`, which rejects the label in exported HTML; visual alignment in the real Tauri window still needs a live check.
- Add a setting: one entry in `REGISTRY` with `kind` (`enum`, `boolean`, `number`, `map`, `list`, `dataSwitch`), `section` equal to the key prefix (`appearance.theme` is in `appearance`), `label`, `help`, `default`, optional `requires`. Adding a key with a default does not bump `SETTINGS_SCHEMA`; renaming or retyping one does, with a step in `migrate.ts`.
- Availability (2026-10-18): one optional attribute, `unavailableUntil: string`, naming the plan step that replaces the setting or brings it back, with the plan's path. Absent means available. `isAvailable(key)` in `registry.ts` is the one place the answer comes from, and everything derives from it: Settings rows and sections, search, export, import, reset, and `readValue`/`writeValue` (an unavailable key reads as its default and takes no other value, so an unavailable data switch is never on; its stored value is kept, unread). Making a data switch unavailable bumps the schema with a step that drops its stored value (schema 4, `offUnavailableSwitches`, derived from the registry). Why one optional string and not an enum: visibility has two states, so presence is the bit; the string carries the exit condition in the plan's own words. No component tests a key to hide itself. No key is unavailable today (law 11); engine slice 4 retired `filtering.dns` and `filtering.perApp` (schema 5, `retireDnsProxy`) and brought `filtering.upstreams` back. The behaviour stays pinned by `src/core/settings/unavailable.test.ts`, which mocks one real key unavailable.
- Anything that changes traffic or the system is a `dataSwitch`: default `false`, `liveCheck: "live_<what_it_proves>"` naming an `#[ignore]`d Rust test of the same name in `src-tauri/src` or `engine/crates` (registry law). Today:
  - `filtering.engine` ("Route traffic through the engine", engine slice 3) -> `live_engine_full_route_relays_and_restores` (`sieve-engine` `control::tests`; it reads the evidence of `scripts/live/engine-route.ps1`, run by the user, and passes when every `control::LIVE_CHECKS` item passed). The engine controller sends it to the engine; off (the default), the engine adds no adapter and no route. The app records its passed check while the engine reports routing.
  - `filtering.systemDns` is gone (2026-10-18, section 0). Settings schema 3: `migrate.ts` `dropSystemDns` deletes a stored value, on or off (`RETIRED_KEYS`), instead of keeping it as an unknown key; law 8 checks it.
  - Per-app Off is not a data switch: it is `apps.levels`, and the engine carries it out per flow.
  - Not a switch: `filtering.upstreams` (list of encrypted upstreams, element shape `upstream`, `parseUpstream` in `src/core/upstream.ts`: `https://host[:port][/path][?query]`, `tls://host[:port][/]`, `quic://host[:port][/]`, the engine's `dns/upstream.rs` grammar, both held to the table `src/data/fixtures/upstream-grammar.json` by `tests/laws/upstream-grammar.test.ts` and the engine's `tests/upstream_grammar.rs`; default the Cloudflare and Quad9 DoH templates). `filtering.userRules` (element shape `rule`, the Filters editor and the log's row actions) and `filtering.exclusions` (strings, the log's row actions), both in `SetPolicy`; `filtering.blockedDomains` and `filtering.allowedDomains` (element shape `domain`, the Filters page).

Never allowed, switch or not (section 0): Windows DNS servers, persistent routes, system or WinHTTP proxy settings, firewall rules that outlive the process. ### Engine workspace (`engine/`)

- DNS on the TUN (`crates/sieve-engine/src/dns/`, `stack/dns_flow.rs`) never sends plain DNS beyond a private server excluded from routing. `dns::Connector` is the only way that code opens a socket: production is `stack::egress::Egress`, tests a recording loopback connector. `tls.rs` is the one owner of TLS settings (versions, key exchange order); every session starts from `tls::provider()`. Tests bind loopback on ephemeral ports with rcgen certificates (`dns/testing.rs`) and never dial `upstream::DEFAULTS`. Live proofs: `docs/live/encrypted-dns.md`.
- Relay CPU experiments are diagnostic only: build `sieve-engine` with `--features relay-experiments`. The feature has no default activation; its settings, batch reader, buffered relay, runtime override and status extension are compiled out without it. The production `relay_tcp`, reader loop and release profile have a source-preservation audit: `node scripts/check-relay-experiments.mjs 4328141e068a6e776e699196eb62802f9c8508f2`. This checks source, not binary or live equivalence. Offline evidence and outstanding checks: `docs/research/2026-10-18-relay-experiments-offline.md`.
- That diagnostic build reads the optional `experiments.json` in the existing admin-only `ProgramData\Sieve\engine` directory, beside `policy.json`, when constructing the engine at service start. Stop, edit, start to compare settings; policy updates do not reload it. The file must be a JSON object. Every field may be omitted; unknown fields, duplicate fields, nulls, non-integer values, out-of-range values or malformed JSON refuse the whole file and restore all defaults. Read errors also fall back with their reason. The contract's inclusive bounds are `tun_mtu` 1280 through 65535 (default 1500), `copy_buffer_bytes` 8192 through 1048576 (omitted: original copy and classifier sizes), `tun_batch` 1 through 256 (default 1, original reader), and `worker_threads` 1 through 64 (omitted: Tokio's unchanged default, including its environment override). For an MTU-only run the entire file is `{"tun_mtu":9000}`; for a copy-only run, `{"copy_buffer_bytes":65536}`. Compare each independently before combining them.
- `tun_mtu` configures both Wintun and ipstack. New batch storage derives from MTU and batch length; slab count derives from the original packet queue plus producer and consumer ownership, with lazy bounded allocation and recycling. A batch begins with a blocking receive, drains only immediately available packets up to `tun_batch`, then crosses the channel once. The TUN heartbeat encloses pool waits, draining and channel backpressure, and ends on delivery or error. The batched reader is joined when its device drops, after unblocking its waits. The existing Wintun ring and UDP datagram buffers are not MTU-sized packet buffers and retain their original sizes; ipstack already sizes its packet buffer from MTU. UDP replies beyond MTU still encounter ipstack's existing UDP write behavior. QUIC, large datagrams and real adapter limits remain live checks.
- `copy_buffer_bytes` selects `copy_buf` over capacity-sized `BufReader`s in both TCP directions, and the classifier's read allocation follows it. The experimental path forwards any bytes beyond the classifier's retention cap before copying the rest. Omission calls the original relay, which remains available in diagnostic builds as the baseline. Under the feature, `status.json.experiments` records the accepted settings, effective `copy_buffers` sizes, `runtime_worker_threads`, and `file: {"result":"absent"}`, `{"result":"ok"}` or `{"result":"refused","reason":"..."}`. A null override means the original implementation/default was selected; explicit effective sizes and runtime count show what that resolves to. This extension is local to the status file, not the pipe protocol.
- The independent E5 build uses `cargo build --profile release-lto -p sieve-engine --features relay-experiments` from `engine/`. `release-lto` inherits `release`, with the experiment's requested `lto = "thin"`, `codegen-units = 1`, and `debug = 1`. `[profile.release]` is unchanged. An installed diagnostic binary can switch all file-controlled experiments by restart; changing the build profile still requires a separate binary.
- Route deletion uses the same classification for named-interface cleanup and journal replay: `NO_ERROR` increments `deleted`, `ERROR_NOT_FOUND` increments `already_gone`, and every other code increments `failed` and `failed_codes[code]`. This includes `ERROR_FILE_NOT_FOUND`, previously treated as absent only by the journal path. Cleanup/watchdog and verb report lines include all counts and the actual per-code map. A journal replay with failures is marked `FAILED` and keeps the journal for retry. These corrections apply to production builds too.
