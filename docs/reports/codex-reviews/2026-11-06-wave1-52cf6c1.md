1. **P1 — “Check again” can install an unseen release.**  
   `engine/crates/sieve-engine/src/update/cycle.rs:87`  
   The request’s meaning depends on the engine’s current status, not the action displayed to the user. Scenario: the UI shows “Check again”; a scheduled check discovers a release before the next UI poll; the user clicks “Check again.” The engine queues `Apply` and can stop the service and close the app. `shown` is copied from server state, so it does not prove the user saw or approved that version. The comment claiming otherwise is unsupported by the tests, which synchronize those states.

2. **P1 — Interrupted rollback can remove the service’s executable path.**  
   `engine/crates/sieve-engine/src/update/swap.rs:162–164`  
   Rollback renames `sieve-engine.exe` to `.failed` before renaming `.old` into place. Power loss between those operations leaves no executable at the registered ImagePath. After reboot, neither the service nor its startup recovery can run; the detached supervisor is also gone. A healthy backup exists, but recovery requires manual intervention. The injected-operation tests resume recovery themselves and do not establish reboot recoverability.

3. **P2 — A refused cycle can already have changed installed data.**  
   `engine/crates/sieve-engine/src/update/cycle.rs:387–395`  
   Each data entry is verified, installed and recorded before the next entry is checked. With valid new `resources` followed by a tampered `list:sensitive`, resources and their version record change, then the cycle returns `Refused`. The UI nevertheless says “changed nothing.” The “every refusal leaves both trees as they were” claim is **reported, not observed** for multiple data entries: its test uses only one data artefact.

4. **P2 — Base64-wrapped private keys bypass the claimed secret scan.**  
   `tests/laws/updates.test.ts:30–34`  
   Wrapped patterns cover recognized headers, but not the secret-key body prefixes. A key with the explicitly supported free-form header `untrusted comment: test`, base64-wrapped and saved under a name without `.key`, passes the scan. A read-only pattern reproduction returned `PlainDetected=True`, `WrappedDetected=False` for both body prefixes. The comment claiming coverage of both witnesses inside wrappers—and the runbook’s corresponding assurance—overstates the evidence.

5. **P2 — Release-number constants impose an unenforced version limit.**  
   `engine/crates/sieve-engine/src/update/trust.rs:46–51`  
   `MAJOR_SCALE=1_000_000` and `MINOR_SCALE=1_000` assume minor and patch components stay below 1000, without deriving or enforcing that constraint. For example, `0.1.1000` and `0.2.0` both become `2000`: the former displays incorrectly, and upgrading between them fails the strictly-newer check. The round-trip test would reject such a build rather than provide support for its valid version.

6. **P2 — Recovery thresholds lack the required derivation.**  
   `engine/crates/sieve-engine/src/update/finish.rs:22–30`  
   `HEALTH_DEADLINE_MS=90_000`, `HEALTH_POLL_MS=500`, `ROLLBACK_TRIES=3`, `ROLLBACK_RETRY_MS=2_000`, `ROLLBACK_PATIENCE_MS=3_600_000`, and `ROLLBACK_PATIENCE_POLL_MS=30_000` have no stated quantitative derivation. Concrete consequence: with a failed new engine and a backup restoration blocked for just over an hour, the supervisor exits before the lock clears, leaving filtering unavailable without intervention. The documents acknowledge that outcome but supply no probe establishing the cutoff, contrary to standard 1.
